# CYCLONE TWIN — PHASE K
## INTERVENTION EXECUTION & OUTCOME TRACKING PLATFORM

> **CRITICAL OPERATIONAL PRINCIPLE**  
> Intervention execution remains human-authorized.  
> Cyclone Twin does not autonomously dispatch emergency personnel.

---

### 1. OVERVIEW & OBJECTIVE

Phase K closes the operational decision loop in Cyclone Twin by transforming top-ranked counterfactual recommendations generated by the deterministic `DecisionEngine` into trackable, human-approved operational interventions. 

Rather than functioning solely as an advisory or forecasting tool, Cyclone Twin now tracks the full lifecycle of physical restoration interventions—from candidate selection and operator authorization through field execution, offline synchronization, deterministic graph restoration, evidence verification, and post-intervention measured vs. expected outcome calculation.

```
DETERMINISTIC RECOMMENDATION (Candidate B)
       ↓
HUMAN APPROVAL (Operator COMMANDER-01)
       ↓
INTERVENTION ENTITY (INT-0042 [APPROVED], Impact Snapshot Frozen)
       ↓
FIELD ASSIGNMENT & EXECUTION (FIELD-TEAM-03 [IN_PROGRESS], Offline Ingestion)
       ↓
FIELD VERIFICATION & PROOF (Photo/Report Validation)
       ↓
MEASURED OUTCOME & VARIANCE (Actual: +87,400 | Expected: +89,000 | Var: -1,600)
       ↓
UPDATED DISASTER STATE (State Version v43)
```

### 2. CORE ARCHITECTURAL DISTINCTIONS

#### 2.1 Candidate vs. Intervention

- **Candidate**: A theoretical intervention generated and ranked by the deterministic `DecisionEngine` (e.g., clearing the Saidapet–Adyar corridor). Candidates are stateless, counterfactual models evaluated against the current graph topology.
- **Intervention**: A binding operational record created when a human operator explicitly approves a candidate. An intervention freezes the expected impact metrics at approval time and tracks execution status, assigned field teams, state transition audit trails, and actual measured outcomes.

#### 2.2 Expected Impact Snapshot vs. Measured Actual Impact

- **Expected Impact Snapshot**: At the moment of approval (`PROPOSED` → `APPROVED`), the expected population recovery, hospital access improvement, and travel time savings calculated by `DecisionEngine` are frozen into the `Intervention` record. Subsequent re-evaluations or model reruns will never mutate what the operator authorized.
- **Actual Impact & Variance**: Upon reaching `COMPLETED`, the underlying road graph is restored deterministically via `NetworkEngine`. Isochrones and population accessibility are recomputed. The actual outcome is calculated as:
  $$\text{Variance}_{\text{population}} = \text{Actual Population Recovery} - \text{Expected Population Recovery}$$
  $$\text{Variance}_{\text{hospital}} = \text{Actual Hospital Recovery} - \text{Expected Hospital Recovery}$$
  $$\text{Variance}_{\text{travel\_time}} = \text{Actual Travel Time Saved} - \text{Expected Travel Time Saved}$$

### 3. INTERVENTION LIFECYCLE & STATE MACHINE

Every intervention transitions through a strict server-side state machine:

```
                  ┌───────────────┐
                  │   CANDIDATE   │
                  └───────┬───────┘
                          │ (Operator Selection)
                          ▼
                  ┌───────────────┐
            ┌────►│   PROPOSED    ├──────────────┐
            │     └───────┬───────┘              │
            │             │ (Approve)            │ (Reject)
            │             ▼                      ▼
            │     ┌───────────────┐      ┌───────────────┐
            │     │   APPROVED    │      │   REJECTED    │
            │     └───────┬───────┘      └───────────────┘
            │             │ (Assign Team)
            │             ▼
            │     ┌───────────────┐
            │     │   ASSIGNED    ├──────────────┐
            │     └───────┬───────┘              │
            │             │ (Start Work)         │ (Cancel)
            │             ▼                      ▼
(Replan Rerun)   ┌───────────────┐      ┌───────────────┐
            │     │  IN_PROGRESS  ├─────►│   CANCELLED   │
            │     └──┬─────────┬──┘      └───────────────┘
            │        │         │
    (Fail)  │        │         │ (Complete & Verify)
            └────────┘         ▼
                  ┌───────────────┐      ┌───────────────┐
                  │    FAILED     │      │   COMPLETED   │
                  └───────────────┘      └───────────────┘
```

#### Valid State Transitions

1. `PROPOSED` → `APPROVED` (Records operator ID, timestamp, and freezes expected impact snapshot)
2. `PROPOSED` → `REJECTED` (Aborts candidate without execution)
3. `APPROVED` → `ASSIGNED` (Binds field team identity, e.g., `FIELD-TEAM-03`)
4. `APPROVED` → `CANCELLED` (Aborts intervention prior to field operations)
5. `ASSIGNED` → `IN_PROGRESS` (Field work commenced)
6. `ASSIGNED` → `CANCELLED` (Aborts intervention prior to field operations)
7. `IN_PROGRESS` → `COMPLETED` (Field completion report received & verified)
8. `IN_PROGRESS` → `FAILED` (Field execution failure reported; triggers deterministic replanning)

*Invalid transitions (e.g., `COMPLETED` → `IN_PROGRESS`, `REJECTED` → `APPROVED`) are strictly rejected with HTTP 400 Bad Request error responses.*

### 4. FIELD EXECUTION, OFFLINE SYNC, & VERIFICATION

#### 4.1 Field Execution & Evidence Ingestion

Field teams receive assigned interventions on mobile field units. Field progress and completion reports are ingested through the existing Phase E/H validation pipeline (`ObservationIngestionPipeline` / `MultimodalPipeline`).

#### 4.2 Offline Storage & Synchronisation

If connectivity is lost in the disaster zone:
1. Field updates (status changes, GPS coordinates, water depth observations, ground photographs) are stored locally in IndexDB / LocalStorage.
2. Upon network recovery, the queued updates are POSTed to `/interventions/{id}/field-update` or synchronized via `/observations/sync`.
3. Valid updates update intervention status and trigger deterministic state recomputation.

#### 4.3 Outcome Verification Mechanism

The system distinguishes **Field Claimed Completion** from **System Verified Outcome**:
- When a field team submits a completion claim, the system evaluates submitted evidence (water level $\le 0.1\text{m}$, clear road photos, road status `OPEN`).
- The `NetworkEngine` restores the segment capacity and recomputes the disaster state version $vN+1$.
- If actual accessibility improves as predicted, outcome verification status is marked `VERIFIED`. Otherwise, it is flagged as `UNVERIFIED_CLAIM`.

---

### 5. FAILURE HANDLING & DETERMINISTIC REPLANNING

If an intervention fails (`IN_PROGRESS` → `FAILED` due to unmanageable flooding or equipment failure):

1. **Audit Preservation**: The failed intervention and all associated evidence remain fully preserved in the immutable audit trail.
2. **Alert Generation**: An `INTERVENTION_FAILED` high-priority alert is automatically posted to `AlertEngine`.
3. **State Recomputation**: The current disaster state remains at its constrained capacity.
4. **Deterministic Replanning**: The system immediately calls `MultiObjectiveDecisionEngine.evaluate_interventions(...)` on the CURRENT disaster state to rank alternative candidate corridors (e.g., Candidate C becomes the new top-ranked recommendation).

### 10. REAL-WORLD DEPLOYMENT LIMITATIONS & GAPS

1. **In-Memory Volatility**: Current architecture maintains intervention state in `AppState` memory for zero-dependency Vercel + Render deployment. Production deployment requires PostgreSQL/PostGIS persistence.
2. **Identity Authentication**: Operator (`COMMANDER-01`) and field team (`FIELD-TEAM-03`) identifiers are verified by API contracts but require integration with government SSO/OAuth2 in real-world deployment.
3. **Radio & Mesh Sync**: Offline synchronization relies on browser storage and HTTP retry. Real disaster deployment would benefit from mesh networking / Satellite SMS gateways.
